# Studio

Use this skill for chat requests beginning with `studio` and for clear requests to connect, disconnect, create, run, resume, or inspect a Studio project. This is a chat workflow, not a terminal CLI. The repository holds shared workflow instructions and scripts. A OneDrive folder added to the workspace, or accessed through a workspace project link, holds every project folder, including its inputs, media, intermediate files, outputs, `LOG.md`, and `DONE`. Do not create or check in project folders or project links in Git.

## Roots and project identity

- Treat the repository containing this skill as the workflow root. Find the separate OneDrive project root among the workspace folders or from the targets of connected project links in the workflow root's `Connected Projects` subdirectory. Resolve connected projects to their real OneDrive paths before running stages by calling `python "<workflow-root>/scripts/resolve_project.py" "<workflow-root>/Connected Projects/<exact-project-folder>"`; for a project supplied directly as a workspace folder, pass that directory instead. Use this read-only helper rather than ad hoc inline Python to resolve paths. It prints the resolved directory and fails for missing paths, broken links, or non-directories. If the project root cannot be found or its identity is ambiguous, ask for its location before creating or changing project data. Do not substitute a directory inside Git.
- Name primary project folders with sequential, stable two-digit IDs: `01-<Name>`, `02-<Name>`, and so on. A pickup or revision of an existing idea is a separate child project beside its parent, named `<parent ID>.<next child number>-<parent name> <purpose>`; for example, `01.1-Love Compounds Too Pickup`. Use `01.2` for the next child of `01`, regardless of later primary projects. Check the OneDrive project root before assigning either number; do not reuse an ID or renumber an existing project. An explicitly requested available ID takes precedence over automatic numbering. A child requires an existing parent.
- Keep project folders only in OneDrive. Add stage and substage directories only when their workflow is defined or run; do not scaffold future stages.
- The stage order is `1-Pre Production`, `2-Production`, `3-Post Production`, `4-Publish`, `5-Analyze`. Substages are numbered within their stage, such as `1-Pre Production/1-Script Review` and `1-Pre Production/2-Cue Cards`. A one-digit prefix such as `1.2` is a stage/substage; a two-digit prefix such as `01.1` is a child project ID.

## Pickup and revision projects

Use a child project when an approved asset needs a new filming or editing pass after work has progressed, such as an extract that does not work in the footage and needs a new filmed take. Keep it scoped to the replacement or related pickup batch. In the child's first `LOG.md` entry, identify its parent project, the specific asset and version being replaced, why the pickup is needed, and the parent source files or edit it uses. Reference those files in place; do not copy the parent's scripts, footage, or outputs into the child merely to restart the workflow.

The child runs the same defined steps with its own candidates, `Approved/`, logs, and `DONE` markers. Its new scripts still require the user's explicit request before writing. A child does not add files to the parent's approved set or change the parent's completion markers. Child manifests fingerprint only the parent artifacts they actually depend on; a changed dependency invalidates the child, not the parent. Preserve earlier exports and store replacement outputs under the child with a clear link to the parent asset and version they supersede. Record the relationship in the parent log if needed, without treating that log entry as a reason to invalidate completed steps.

## Commands

For the connection script, use an available Python 3.9+ interpreter (`python` on this Windows machine, typically `python3` on macOS).

For full workflow validation and recording, use a Python 3.10+ environment with the relevant stage's validation dependencies installed. Missing interpreter features or dependencies are reported as unverifiable; validation does not install them or fall back to an agent's judgment.

- `studio connect <project>`: use the exact project folder name and run `python "<workflow-root>/scripts/connect.py" connect "<project>"`. The script finds the synced `OneDrive/Books/Parent Like a Millionaire/Marketing/Studio` root using Windows OneDrive environment variables or the usual Windows/macOS locations, including macOS `~/Library/CloudStorage/OneDrive*`. It creates the `Connected Projects` subdirectory in the workflow root when missing, then creates a directory symlink with the project's folder name inside it; when Windows denies symlink creation because of missing privileges, it falls back to a directory junction. Several projects may be connected at once; reconnecting the same target is harmless. If the script reports several OneDrive roots or cannot find the root, ask for the intended local Studio project-root path and pass it with `--project-root`. Never replace an existing workspace entry or guess between roots. Connecting only adds the workspace link; it does not copy project data or edit `Studio.code-workspace`.
- `studio disconnect <project>`: run `python "<workflow-root>/scripts/connect.py" disconnect "<project>"` with the exact project folder name. Remove only that project's link in the workflow root's `Connected Projects` subdirectory, preserving the OneDrive folder and all its contents. An absent link is already disconnected. The script can remove broken project links and refuses files, real directories, and links to unrelated targets. If the link was created with an explicit `--project-root` outside the automatically detected locations, pass that same root when disconnecting; ask for it if unknown.
- `studio create project "Name"`: resolve the next primary project number, or use an available ID explicitly given by the user. Create the project root and only the first step, `1-Pre Production/1-Script Review`, in OneDrive. Create `Approved/` immediately in the step folder, even if it has no files yet. Do not create later-stage folders or write candidate scripts unless the user explicitly asks for them. When creation follows an intake chat, carry the agreed source and candidate ideas into the project's log.
- `studio create pickup <parent> "Purpose"`: resolve the parent project and next child ID, then create the child with the same initial 1.1 structure. This is also the route for natural-language requests to repair an asset within an existing idea. Record the parent and replacement scope in the child's log; do not modify the parent's approved files. If the user explicitly names an available child ID, use it.
- `studio run <stage.substage> [project]`: resolve the real project, then run the shared validation command with `--stage <stage.substage> --prerequisites`. Stop if an ancestor is not current; do not run or install the requested stage to repair a prerequisite. Use the shared stage audit to reuse a current target. When an incomplete/stale target is selected for execution, invoke the common invalidation transition below, then read its skill and run its workflow. A missing target `DONE` is not a prerequisite failure. Do not invalidate anything merely because preflight rejected the requested stage.
- `studio run [project]`: run the shared validation command for all stages, then resume the first incomplete step in dependency/workflow order. Continue with shared prerequisite validation and completion recording until a skill is missing, a step fails, or human input or review is required. Do not rerun AI work for ancestors whose Python evidence is current. At 1.1, discuss a new asset slate interactively and stop before writing scripts unless the user explicitly requested that writing. Do not silently skip an undefined step.
- `studio status [project]`: run the shared validation command for all stages and report its current, stale, missing, blocked, or unverifiable evidence and next required action. Status is read-only: do not delete, archive, migrate, or rewrite project markers or outputs while reporting status.
- `studio clear stale <stage|stage.substage|all> [project]`: only on an explicit cleanup request, read and follow [Studio Clear Stale](../studio-clear-stale/SKILL.md). Delete only the selected project's matching `STALE` directories; `all` covers all numbered stages and substages in that project. This does not validate or change active completion or outputs.
- `studio override <stage.substage> [project]` or `studio override all [project]`: only on an explicit manual override request, read and follow [Studio Override](../studio-override/SKILL.md). This separate workflow previews acceptance of existing outputs without rerunning stage success checks, then requires confirmation through the question tool before applying. Never infer override permission from a run, status, or tool request; no general `--yes` or implicit automatic override is supported.

Resolve primary and child projects by their full ID or exact folder name. If a title could mean both a parent and one or more children, ask which one to run or inspect.

The stage skills below are shared workflow definitions in this repository. Read the relevant source skill before running a step. Record project-specific decisions in the OneDrive step `LOG.md` or its working artifacts; update the shared source skill when the workflow itself changes. A step skill may describe interactive or judgment-based agent work; scripts are optional. Each step skill must state what it does, its success condition, and how to rerun without duplicating or overwriting valid work. Each defined step's `dependencies.json` is the sole machine-readable source of its prerequisite stages and input/output inventories; the skill describes the human workflow rather than maintaining a second dependency list. The step creates its own output, debug, and intermediate directory structure in the matching OneDrive path when needed.

The mandatory normal run/status validation command is `python "<workflow-root>/scripts/validation.py" --project-root "<real-project-root>" [--stage <stage.substage>]`. Add `--prerequisites` with `--stage` to validate ancestors without requiring the target to have a marker. It walks JSON prerequisites, checks common fingerprints and inventories, then invokes the stage's declared `scripts/validation.py` subclass of `StageValidation`. Overrides implement `validate_stage()` without bypassing common checks. Validation never generates files, writes logs, changes markers, installs dependencies, or invokes AI. The old `scripts/stage_status.py` entry point delegates to this command. Results distinguish current, missing, stale, blocked, unverifiable, and explicitly skipped stages. Prerequisite rejection must stop before generation and must not itself invalidate or rewrite upstream markers.

The explicitly confirmed [manual override](../studio-override/SKILL.md) is a separate attestation path, not a normal completion check or automatic repair. Normal status honors its snapshot only until declared inputs, outputs, full watched inventories, or workflow files change. It does not waive normal tool permissions or external-path approval.

All substage completion recording uses `scripts/stage_completion.py`, never agent-authored `DONE` JSON or a direct stage-local write. For inventory/approval stages 1.1, 1.2, 1.3, 2.1, 3.1, and 3.6, after the stage's success condition is satisfied, run `python "<workflow-root>/scripts/stage_completion.py" record --project-root "<real-project-root>" --stage <stage.substage>`. It builds portable evidence from the JSON definition, fingerprints stage implementation and common flow scripts, checks ancestors, and runs the same common and stage-specific validators on the candidate before writing anything. A scoped sync run, cue-card preview, pending approval, or XML generation alone cannot bypass these checks. Stages 3.2 through 3.5 supply their richer stage-owned manifests to the same `record_done` Python API from their normal checkers/generators; use those scripts rather than inventing their conditions. The optional `--evidence <manifest.json>` CLI accepts equivalent stage-owned evidence but does not skip validation. Record attempts and handoffs in the normal append-only log.

The writer reuses unchanged evidence without rewriting the marker, and writes changed evidence atomically while preserving the previous active marker in `STALE/N/DONE`. Changed/new completion also archives dependent completion through the common graph invalidator, even when the target previously had no active marker. Recording is serialized by a per-stage `.DONE.lock`; an existing lock causes a clear failure and is never automatically removed. If recording was interrupted, inspect its lock and temporary file before retrying. The previous active marker remains visible until its replacement is published. Recording clears its own pending invalidation pointer only after successful completion. It never generates or moves outputs and is not a manual override.

Definitions declare required implementation files in `workflow_dependencies`, using workflow-root-relative paths. New evidence cannot omit those fingerprints. Rich-manifest stages declare `completion.stage_owned` so generic inventory-only recording is refused; their normal checker/generator or explicitly supplied, fully validated evidence is required.

Stage 1.4 also uses the generic shared `record --stage 1.4` command after its registry validator passes. Its canonical pair is human-only compact `Asset Registry.md` cards plus machine-maintained `Asset Registry.json` evidence. Both are required, fingerprinted, protected outputs, never disposable generator-owned artifacts. Its human gate is each asset's in-place Review field, not an approval-folder move; empty/all-rejected slates require recorded explicit human confirmation. Only the current plain-newline card format is supported. Historical backups and opaque JSON migration evidence remain passive history, not active registry formats. This independent branch does not add a prerequisite to presenter production or postproduction stages.

Stage 2.2 uses `broll.py complete --project-root "<real-project-root>"` from its own skill's scripts directory to supply nested, stage-owned evidence to the shared recorder. Generic inventory-only recording is refused. Its collection gate is at least three distinct usable video candidates per current approved B-roll asset, assessed against the latest logical brief revision and required shot coverage; there is no separate human clip-selection gate. Each asset has one append-only `request.md` containing the initial verbatim registry brief, later creative revisions and chronological search attempts/outcomes. Actual searches use `broll.py search`; `search-note` appends review outcomes and next-term rationale. Search-only entries do not change brief applicability or invalidate candidate suitability. The schema-2 ledger checks exact journal bytes and event offsets; completion watches journals, candidate ledgers and videos. This actively developed format has no automatic migration from earlier versioned-request schemas. Manual family footage may remain pending. This independent branch depends on 1.4 and does not block existing presenter filming or postproduction. Preserve journal history, candidate records and footage across ordinary refinements; they are not generator-owned outputs.

## Parallel work within a substage

Keep the existing substage prerequisite and completion gates. Within the selected substage, use available agents for independent work when it will help. This instruction authorizes delegation during normal Studio execution; no separate user request for agents is needed. If agents are unavailable or the work is too small to benefit, execute it directly.

In Kilo's VS Code extension, prefer visible Agent Manager sessions created through `agent_manager` in `local` mode, one per independent task. Keep every worker in the coordinator's existing workspace/project root so the user can follow each session in the Agent Manager panel. Do not create worktrees, branches, or separate checkouts for delegation. Give sessions descriptive names identifying the substage and script or recording group where the tool supports naming. Use the available session inspection and communication tools to collect results before completing the stage; merely starting a session is not a completed handoff. If visible local sessions are unavailable, use native subagents when available. In other hosts, use their native agent delegation tools. Each worker executes only its assigned unit and must not recursively launch a fresh whole-stage Studio run or additional worker sessions.

Before calling generation helpers, read the substage skill and `dependencies.json`, inspect the current input/output inventory and relevant helper interfaces, and identify concrete independent work units. Read-only Python discovery and prerequisite validation may run first. Use the helpers' actual filename matching and grouping rules rather than guessing relationships from prose. Group outputs that share context or must be produced together into one task; separate filenames alone do not prove independence. Revalidate and reuse existing work before considering generation.

- Give each worker the resolved project, substage instructions, exact input files, exclusive output scope, supported command or workflow, and expected result. Workers must preserve human edits and report outputs, checks, and failures to the coordinator. Workers may not start later substages.
- Delegate only work with disjoint writes and stable shared inputs. Check whether helper invocations also change logs, manifests, archive pointers, completion records, shared plans, or caches; a scoped output option does not by itself make concurrent invocation safe. Keep such mutations serialized through the coordinator. Use isolated previews only when the stage supports them and its normal publication path can consume the results.
- Use supported scoped execution when available. If a helper processes the entire stage or couples computation to shared mutations, keep that helper serial; do not launch duplicate whole-stage runs, invent flags, bypass normal recording, or modify Python merely to force delegation. Independent analysis or review can still be delegated.
- Bound concurrency by available agents and machine resources. Preserve stage-specific batching requirements, such as loading a transcription model once for all requested audio. Never retranscribe or regenerate valid outputs to create parallel work.
- The coordinator joins all workers, reconciles results, serializes required publication, archiving, and log writes through existing helpers, then runs the normal full-stage checker/recorder. A worker's success is not stage completion. If any task fails or needs human review, preserve successful work and follow the stage's normal failure or handoff flow; do not advance through the gate.

## Invalidation and regeneration

All execution-time invalidation uses `scripts/stage_invalidation.py` through `python "<workflow-root>/scripts/stage_completion.py" invalidate --project-root "<real-project-root>" --stage <stage.substage> --reason "<reason>"`. It starts from the explicit step ID, follows reverse JSON dependency edges, and moves each affected active marker into that step's next unused `STALE/N/DONE`. Containing stage-level completion is also archived. Known independent branches are preserved; unknown later numbered step folders are treated conservatively. It works even if the failed step never had a marker. It logs reasons and preserves outputs, sources, and human edits in place. No handler may delete `DONE` or implement a separate dependency walk.

Definitions declare a separate `generated` inventory for artifacts Studio can replace. This is not the same as completion `outputs`: intake originals and human-approved files are not generator-owned. Before deliberate regeneration, use the stage's explicit `--overwrite`/`--regenerate` option where provided, or `python "<workflow-root>/scripts/stage_completion.py" prepare-regeneration --project-root "<real-project-root>" --stage <stage.substage> --reason "<reason>" --file "<project-relative-generated-file>" [--file ...]`. Select only existing generated files actually being replaced. The helper invalidates markers and moves those files into the same pending `STALE/N/`, preserving their paths relative to the step folder. It preflights the whole selection, refuses inputs/protected approval files and archive collisions, and never sweeps a directory or the dependent stages' outputs. Generated First Cut XML is also a render input (`role: "project"`) and may be archived explicitly; approved movies may not.

`STALE/PENDING.json` identifies the exact unfinished invalidation slot; its `EVENT.json` records whether there was a previous completion marker. Marker-only retries and noncolliding regeneration selections reuse that slot rather than guessing from the highest archive number. If another deliberate regeneration replaces an artifact already archived by a completed preparation, allocate a fresh numbered slot, preserve the prior completion baseline, and link the previous slot in the new event; never overwrite earlier archives. Unrecorded destination collisions and races still fail safely. Numbers advance above remaining numeric archive names, so manual deletion does not recycle gaps or confuse chronology. A regeneration without prior completion can have an output-only slot. Successful recording clears the pointer, not the archives. Do not delete an active pending slot during recovery; finished archives can be removed manually in OneDrive. An explicit `studio clear stale` request deletes the selected archive directories, including pending slots, through its separate cleanup skill. Studio never purges `STALE/` automatically. Archived artifacts never count as current inputs, outputs, approvals, or latest review versions.

Do not move files on status/preflight or on failure alone. Preserve unchanged valid outputs. Differing human-editable outputs still require the stage's deliberate replacement/review decision; archiving is not permission to silently regenerate them. Versioned Takes reviews retain their normal latest-version workflow. Isolated trials and previews do not invalidate or archive canonical project work; `0-Tmp` folders are independent scratch rather than unknown workflow steps. Preview destinations cannot be canonical stage, approval, or archive folders, and preview publication must not modify aliased canonical files.

Human approval should use a file moved into an approval folder, with the input fingerprints and approved output fingerprints recorded in completion evidence. Preserve existing `Approved/` naming for 1.1; 1.3 shortlist Markdown and 3.6 edited, rendered movies use `APPROVED/` within their own stage folders. FCPXML files are 3.6 inputs, not approved render outputs. Do not rename or move project folders automatically. Stage 1.2 has no human gate: existence of the expected PPTX files suffices alongside common fingerprint validation. A future stage without a defined approval structure must declare `validation.skip_reason` rather than infer approval or invent an attestation. Skipped prerequisites block dependent validation; skipping is not success.

## Logs, completion, and invalidation

Stages with supported independent jobs may use the common archive helpers' `job_id` parameter. Their pending pointers live at `STALE/PENDING/<SHA-256-of-job-id>.json`, record the exact job ID, and reference distinct numeric archive slots with explicit stage-baseline provenance. The existing `STALE/PENDING.json` remains the stage-wide baseline and legacy recovery pointer. Shared mutations are serialized by the local project's `.studio-mutations.lock`, not by the existence of pending files. Successful completion validates all own-stage pointers before publication and clears them after success, preserving archives and dependent-stage pointers. Concurrent workers must be joined before completion; stage-specific active-job checks may enforce this. These filesystem locks are local-host coordination, not cross-machine OneDrive locking.

- Each executable step has one human-readable, append-only `LOG.md` in its OneDrive step folder. Append an entry for every attempt, validation failure, human handoff, and invalidation. Record inputs, actions and decisions, outputs, result, and the next action. Preserve prior entries.
- Append entries with `python "<workflow-root>/scripts/append-log.py" "<step-folder>/LOG.md" --title "<heading>" --item "<bullet>" [--item "<bullet>" ...]`. Run it directly against the connected project, requesting external-path approval when required. Do not copy the log into the repository, rewrite the whole file, or use shell redirection. The helper performs one append-only write and refuses non-`LOG.md` targets.
- Each completed step has a `DONE` file in its OneDrive step folder. `DONE` is a small machine-readable manifest of the step's declared input dependencies, required output files, and relevant directory conditions, with their expected paths and fingerprints. Include the step skill and script revision when changes to them would change the result. Exclude the shared Studio root skill (`.agents/skills/studio/SKILL.md`), `LOG.md`, `DONE`, `STALE/`, and incidental debug or temporary files from fingerprints. Adding stages or changing the overall workflow must not invalidate completed stages. For migrated steps, `studio.fingerprints.identity` records MOV, MP4, M4V, MKV, AVI, WEBM, MXF, and WAV media using byte size and integer Unix modification seconds; all other files use SHA-256, with the method declared in the manifest. Existing SHA-256 entries retain their original meaning. Known text formats use SHA-256 after CRLF-to-LF normalization; preserve encoding, BOMs, lone CRs, whitespace, and trailing-newline presence. Non-media binary files (including Office containers, archives, and models) remain byte-exact. Validators accept canonical hashes and existing exact-byte legacy fingerprints, without rewriting saved source identities merely to adopt the convention.
- Every new `DONE` path must be portable: store project artifacts as paths relative to the resolved OneDrive project root with `scope: "project"`, and shared skills/scripts as paths relative to the workflow repository root with `scope: "workflow"`. Use forward slashes. Apply the same rule to paths nested in `inputs`, `outputs`, `dependencies`, and conditions; a condition's bare path string is project-relative unless it explicitly declares a different scope. Never write absolute macOS/Windows paths, drive letters, symlink locations, `..` escapes, or machine-specific cache paths into `DONE`. Resolve and confine each path to its declared root before fingerprinting or validating it.
- When validating older `DONE` manifests, ignore any legacy dependency entry for the shared Studio root skill without editing the record. A changed hash for that file is not an invalidation reason. New completion evidence omits it. Continue checking the stage's own instructions, scripts, inputs, outputs, and directory conditions as declared; insufficient legacy evidence is reported rather than silently migrated.
- Write `DONE` through the shared recorder only after checking the step's success condition and verifying its outputs. Read-only preflight/status do not mutate markers. Execution failures and deliberate regeneration use the common invalidation API; active markers are archived, never deleted. Archived markers are historical evidence, never active completion.
- A failed step invalidates every direct/transitive dependent according to the JSON graph, plus containing stage-level completion, even without its own marker. The common helper logs each affected step and preserves known independence. Outputs stay in place unless a deliberate regeneration explicitly selects generator-owned files for archiving. Resume from the first invalid step.
- This validation occurs when Studio is invoked, not continuously in the background. A `DONE` marker cannot undo an external action such as publishing; a rerun of such a step must reconcile the external result before acting again.
- A stage-level `DONE` may be written after all its defined substages are complete. It does not replace the substage markers used for resuming.
