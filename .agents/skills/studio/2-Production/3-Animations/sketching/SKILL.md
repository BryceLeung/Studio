# Sketch Animation Asset

## Meaning and scope

"Sketch" means a quick image preview for rapid visual iteration, not a finished object or Remotion render. Use this skill when the user asks to sketch something or requests a quick image preview. Read the parent [Animations skill](../SKILL.md); resolve the current project and registry asset and follow its prerequisite, mutation, permission and append-only logging rules. A text proposal or stage setup alone does not authorize sketching. If a bare "preview" request is ambiguous, default to a quick static sketch, not an expensive video render.

AI image generation and image editing are allowed for sketch exploration, including reference-guided design variations and focused revisions. Programmatic drawing and deterministic edits remain available when appropriate. This permission is limited to static sketches; it does not enable automatic animation generation or change render/save gates. Do not invoke Remotion, bundle React, open Remotion Studio, render MP4, or extract a frame from video to make a sketch. Do not create a candidate's Studio entry, timeline, snapshot or render settings for a sketch.

## Tool availability and permissions

Use an actually connected image-generation/editing tool or a configured provider API with normal execution, network and filesystem approvals. Permission to use AI does not mean a tool, account, API key or billing is available. Do not invent a tool, model, endpoint or successful generation. Do not install dependencies, configure providers, incur new subscriptions or start paid API requests merely to update these skills. A sketch request may use an already configured provider under its existing permissions and spending limits; otherwise report the missing setup before generation. Never expose credentials or save them in project provenance. If no suitable image tool is available, explain that limitation rather than silently substituting a low-fidelity coded illustration for an AI-assisted request. Offer programmatic drawing only as an explicitly identified alternative.

## Fast image workflow

1. Inspect the current discussion and only the source context needed for the requested visual. Resolve an unambiguous registry asset and subject. Use a safe single-directory object name and the next unused version under `2-Production/3-Animations/<registry-id>/sketches/<subject>/vNNN/`. Create the asset's missing `sketches/` through the maintained initializer. Never move, rename or overwrite earlier sketches or historical candidates.
2. Create one clear static view of the requested idea at a modest supported resolution, normally around 960 pixels on the long edge. For illustrated character exploration, prefer a suitable connected image tool over primitive coded approximations. For revisions, use the selected prior sketch as image input and reference-guided or masked editing when supported, specifying what must stay unchanged. Never promise exact identity or pixel preservation from a generative edit. Change only the requested aspects and inspect for drift. Do not regenerate unrelated variants or produce large batches unless requested. Treat uploaded reference images as design inputs, preserving the originals and recording whether the result is an original concept, source-derived edit or programmatic drawing; generation does not establish licensing rights.
3. Keep the image focused on the subject. Avoid presentation boards, decorative grids, long callouts, alternate views, polished motion controls and other work that slows iteration unless requested. Save the returned image in the version directory and create `preview.png` for review; preserve the provider original if conversion is needed. Retain a short `provenance.json` beside it with the exact user request, submitted prompt/edit instructions, provider/tool and actual model when reported, generation/request ID and settings when available, and project-relative input reference/parent-sketch paths. Record omissions as unavailable, not invented facts. Keep drawing/editing source when code was used; do not fabricate editable source for a flattened AI image. No production-ready rig or full candidate scaffold is required.
4. Open the actual PNG for a quick check of readability, completeness and clipping. Present it with the sketch version and at most a short explanation, then stop for feedback. Record the exact request, project-relative path and handoff in the stage log; do not invent render/probe evidence. Changes after delivery create the next unused sketch version, leaving earlier images and sources untouched.

For simple programmatic sketches or deterministic edits, Pillow in the shared root `.venv-tools` remains supported. Keep a short self-contained script in the sketch version and use normal editing/execution approval. This drawing-only environment choice does not change the stage validation interpreter. Do not install dependencies automatically, fall back to Remotion or claim Pillow can rasterize SVG or perform generative editing.

## Render and save boundaries

Sketch acceptance is not permission to render or save. A generated PNG is a concept image, not automatically an editable character, separated layers or an animation rig. Before a requested render, identify the preparation needed and report any unsupported conversion; never claim automatic faithful conversion into animation parts. A later explicit "render" request follows [Render Animation Object](../object-authoring/SKILL.md), creating a separate Remotion candidate that records the selected sketch as its design reference. A later "save" request follows [Save Animation Object](../library-save/SKILL.md), which copies a selected candidate, not a sketch, to the shared library. If only a sketch exists, explain that it is not yet a reusable rendered candidate; do not silently render or promote it. No full-animation source, approvals or completion markers are changed by sketching.
