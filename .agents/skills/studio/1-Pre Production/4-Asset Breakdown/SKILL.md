# 1.4 - Asset Breakdown

Read the Studio root skill and this stage's `dependencies.json`. Resolve the real OneDrive project and run shared prerequisite validation before work. This is an independent preproduction branch, not a gate on presenter filming/editing. Never generate project artifacts merely while implementing or testing this workflow.

## Workflow

Both intake modes read and fingerprint ALL approved scripts from 1.1 only. Never read or parse extracts or the 1.3 shortlist for this stage, including context, reconciliation, inspection, coverage, or completion. Stage 1.3 is not a prerequisite. Missing, malformed, or changed extract files have no effect on this branch.

### Script-only switch

For `studio run 1.4 --script-only [project]`, or an explicit request to disable automatic suggestions for this run, skip editorial AI proposals and import only explicit script requests. Run `python "<helper>" reconcile --script-only --dry-run --project-root "<project>"`, then the same command without `--dry-run` after normal prerequisite auditing. No suggestions scratch file is needed; `--script-only` and `--suggestions` are mutually exclusive. This is a per-run choice, not a change to the default workflow.

Script-only intake imports every nonempty Stage Directions cell in a recognized three-column script verbatim as one User-origin asset per row, plus all anchored `Asset:` Word comments. Each direction uses that row's spoken dialogue range and stable row ID, with `extracts: []`. Directions starting with `Animation:` (case-insensitive, ignoring leading whitespace) receive type `Animation`; all other directions receive type `Other`, which is valid without a required human type choice. Preserve the full direction, including the prefix, as the brief. It does not infer extra visuals or rewrite human instructions. These explicit imports auto Keep under the rule below; performance-only directions may still be rejected by the human. A direction-only row with no spoken dialogue fails explicitly; move its direction to the relevant dialogue row rather than guessing an anchor. Non-three-column scripts retain comment-only intake. Direction text remains excluded from spoken word counts. Context and indexed context expose directions for inspection even in the default mode; normal suggestion-based runs still import only comments automatically.

The selected intake mode is saved in registry control evidence so inspection and completion validate the same imported sources. Existing AI proposals omitted by this run become inactive, retain their IDs/history/human fields, and require rejection during review. Switching back to suggestion-based reconciliation also retires script-only direction cards not present in that mode. After the one-time pending-import approval transition, unchanged script-only reruns preserve decisions and file mtimes. All normal protected-publication, review, empty-slate confirmation and shared completion gates still apply. Do not reuse a current default-mode result instead of carrying out an explicitly requested mode change; perform the normal deliberate invalidation/reconciliation transition. An all-imported valid kept slate can pass check and shared completion in one run without another human-review handoff; the intake switch alone never records completion.

### Explicit import approval

The user authorizes automatic approval of notes taken directly from the approved scripts. During reconciliation, active User-origin stage directions and anchored `Asset:` comments auto `Keep`, including unchanged existing imports still marked `Pending Review`. New AI proposals remain `Pending Review`; changed AI proposals retain the normal renewed-review policy. Changed explicit imports (brief, range, source fingerprint or applicability) also auto `Keep`, but an explicit human `Reject` is preserved even after changes or return to the active slate. Preserve human-edited fields with the normal three-way merge and record prior rows/decisions in history for changes and pending-import approvals. `Other` is a valid imported type, not an outstanding review requirement. Retiring imports are not auto-approved or auto-rejected: normal inactive/review/rejection policy applies. Auto Keep does not waive malformed-source/registry checks, valid anchors/fields, exact current inputs, complete imports, prerequisite validation, inactive rejection, empty/all-rejected human confirmation, or the shared recorder.

Use Python 3.10+ and the standard library. Helpers live beside this skill under `scripts/assets.py`. Supported commands are `context`, `reconcile`, `inspect`, `check`, and `confirm-empty`. All paths below are resolved paths, not a new terminal `studio` command.

For three-column approved scripts, `studio/script_docx.py` identifies the spoken column; word indices and asset-comment passage anchors exclude IDs, directions, table headers, and review front matter. Stage directions are nonspoken production context, not additional script words. Anchor an `Asset:` comment to the relevant spoken passage rather than only to a direction or ID; an excluded-only comment cannot supply a spoken range and fails explicitly. Existing headingless legacy script reads retain their original indexing behavior.

Extracts remains only for artifact compatibility; new proposals display `Full film only`. Do not assign extracts as part of intake or editorial analysis. The shipped registry header and legacy ID syntax remain readable, but do not authorize extract lookup or assignment. Empty and trailing-newline rationale values are preserved. Unsupported ambiguous syntax, unknown text, duplicated fields, deleted cards, changed IDs, and altered read-only labels fail explicitly rather than disappearing on save. There are no per-field headings, per-card machine blocks, or metadata footer. All source keys, paths, ranges, active/change flags, provenance, proposals, input evidence, history, control and migration snapshots live in `Asset Registry.json`. ## Asset brief guidance

New project registries use stable IDs `A01` through `A99`, with a hard limit of 99 assets across all scripts and asset types in that project. Imported user comments count toward the limit. Rejected and retired assets retain their IDs; never recycle IDs or bypass the cap by splitting a proposal batch. Both dry-run and publication reject additions beyond the limit before writing the registry. If the slate exceeds the available IDs, report the limit and ask which proposals to omit or consolidate. Existing registries retain their legacy `ASSET-000001` IDs and numbering policy; do not migrate or rename their assets.

For agent-proposed B-roll and stock image opportunities (`Still`), write the `brief` using these four labels, in order, as ordinary prose within the existing Asset field:

- Purpose: State what the viewer should understand or feel, tied to the source passage and its surrounding script. Explain the asset's role rather than simply restating the spoken words.
- Tone: Describe the emotional tenor, such as compassionate, reassuring, tense, or joyful. Tone alone is insufficient without a passage-specific purpose.
- Possible visuals: Offer a few broad, meaningfully different visual directions. Explicitly label them optional alternatives and allow other visuals that fulfil the same purpose and tone. Avoid prescribing an exact action, sequence, camera move, or prop unless essential to the passage. These examples are neither required shots nor a mandatory montage.
- Requirements: State only essential constraints supported by the script or explicit human instructions, such as actual-family footage, a necessary subject, privacy, authenticity, or exclusions. If none are specified, say so; do not turn an example into a requirement.

Example brief: Purpose: Convey an adult child offering an ageing parent care and reassurance. Tone: Compassionate, intimate, everyday. Possible visuals (optional alternatives; other visuals serving the same purpose and tone are welcome): Son holding dad's hands; sitting quietly together; offering practical help with an everyday task. Requirements: No additional requirements specified.

Keep the `notes` / Why field for the editorial rationale and connection to the anchored passage. Use the existing `brief` and `notes` fields; do not add registry fields, per-field headings, or a new asset type. During review, check that a suitable alternative could satisfy the B-roll or stock image brief without reproducing any one example exactly.

Animation and cartoon briefs may be specific about characters, actions, sequence, composition, timing, and visual details because those assets can be created to the brief. Still explain their purpose and script connection; the broader stock-sourcing format is not required for authored animation or cartoons, including an authored cartoon still.

Preserve imported user-origin briefs verbatim under the comment-import rules above. Do not silently broaden an explicit human requirement or rewrite an existing human-edited brief into this format. If a requirement's meaning or whether an action is mandatory is unclear, ask the user before changing it. This guidance governs new agent proposals; it does not authorize rewriting existing project registries.

## Reruns and Scope

Compact cards use plain newlines, not trailing backslashes, trailing-space hard breaks, or HTML breaks. Keep card source compact: no blank line after its heading or between related metadata lines. Asset and Why values start beside their labels and may contain human-authored multiline paragraphs. Keep the blank line after the passage blockquote, and one blank line between cards and after the introduction. Fenced fields, per-field headings, embedded metadata, spaced cards, and hard-break cards are unsupported; there is no conversion or reformat command. Literal escaped backslashes in prose remain supported.

The optional JSON `migration` field is opaque historical evidence. Helpers preserve and checksum it without interpreting its contents, accessing its referenced backups, or using it for review or completion decisions. It is passive history, not executable format support.

The registry Extracts field and JSON schema remain for shipped artifacts and downstream consumers. Existing or human-edited references are inert metadata: only list/string/uniqueness and existing card syntax are validated, never extract existence, source, intersection, or coverage. They are not verified applicability claims. New comment, direction and AI proposals use `extracts: []`. On reconciliation, the normal three-way merge clears unedited old proposal references, preserves human-edited references and other fields, and records changed proposals/inputs and prior decisions in history under the approval rules above. Historical input snapshots may mention the old shortlist until reconciliation replaces the current snapshot with approved scripts only; those historical paths are not read.

Reconciliation preserves existing human field edits, JSON evidence and rejection history. Active explicit imports follow the auto Keep / preserve human Reject rule above; AI proposals and retiring assets retain the normal review reset on changed underlying proposal, range, input fingerprint or applicability, recording the prior decision. Unchanged reruns preserve both files and their mtimes after any pending-import approval. Human edits to brief/type/notes/anchors are merged field-by-field rather than overwritten; inspect Proposal for source changes and preserve human fields, with structural validity still required by check. Existing AI assets omitted by the new analysis are retired and never automatically resurrected as new IDs. Comment identity is script-relative path plus Word comment ID, not its changing text. Renaming a script is a new source and retires the old asset. Removed inactive cards stay in the registry to prevent duplicate imports and retain history. Save editor changes before helper mutations; do not edit concurrently with publication. Missing, malformed, checksummed-tampered or identity/label-mismatched JSON fails rather than being regenerated. Markdown human fields are not checksummed against JSON and remain editable.

Pair publication cannot be atomic: each changed file is replaced atomically while `.assets-publication.json` blocks readers. A failed replacement rolls back already replaced files from byte-exact temporary backups. If interrupted or rollback fails, the guard and `.assets-recovery-*` files remain: stop, inspect the guard's target/previous mapping, restore both previous files (a null previous means the target did not exist), verify the restoration, then remove the guard before retrying. Never simply delete the guard and accept a potentially torn pair.

This stage plans assets only. It does not acquire media, manage later media versions, license files, assign final edit timestamps, or own downstream asset approval. Coverage is a union of kept word ranges, not a measure of production quality or a requirement to fill every frame.
