# 1.4 - Asset Breakdown

Read the Studio root skill and this stage's `dependencies.json`. Resolve the real OneDrive project and run shared prerequisite validation before work. This is an independent preproduction branch, not a gate on presenter filming/editing. Never generate project artifacts merely while implementing or testing this workflow.

## Workflow

Use Python 3.10+ and the standard library. Helpers live beside this skill under `scripts/assets.py`. Supported commands are `context`, `reconcile`, `inspect`, `check`, and `confirm-empty`. All paths below are resolved paths, not a new terminal `studio` command.

1. Audit existing completion through the shared validator. Reuse a current stage. For selected incomplete/stale work, use shared `stage_completion.py invalidate --stage 1.4` with the normal project-root/reason arguments. Preserve both canonical files, `Asset Registry.md` and `Asset Registry.json`, in place. Neither is a `generated` artifact; never use prepare-regeneration on either. Only the current compact Markdown/JSON pair is supported. Historical project backups are not active registries and must remain untouched.
2. Run `python "<helper>" context --project-root "<project>"` for JSON containing portable input fingerprints, every approved script's words, imported `Asset:` Word comments and their highlighted ranges, and approved extract passages mapped back to script word ranges. Also run `python "<helper>" context --indexed --project-root "<project>"` for readable editorial text with every exact script token numbered and comment/extract ranges alongside their briefs/passages. Both are read-only. Word indices are zero-based, inclusive, and restart for each script. Use the normal JSON's exact input snapshot in the suggestions envelope; do not reconstruct it from the readable view. Review all inputs, including scripts with no asset comments or suggestions. Only comments beginning with `Asset:` (case-insensitive, allowing leading whitespace) are imported; preserve the full description after the prefix as the brief and retain the original comment text in provenance. Ordinary comments are ignored. Word comment range markers anchor the highlighted script passage; arbitrary color-only highlighting without an asset comment has no brief to import. A prefixed comment with no anchored script range, including one whose range was deleted, fails explicitly so asset intent is not silently lost. Restore its range or resolve its intent with the human before retrying. Empty asset descriptions and malformed or ambiguous ranges also fail rather than inventing provenance.
3. Perform the editorial analysis as an agent. Suggest useful B-roll, graphics, stills, animation, screen recordings, audio, or other supporting assets. Aim for roughly 25% of full-script words and 100% of approved-extract words covered by useful assets; these are advisory defaults, never quotas or completion gates. Avoid decorative suggestions just to meet a percentage. Import every anchored `Asset:` Word comment as user-origin; a human can reject it. Do not import ordinary review comments or relabel a user asset comment as AI.
4. Validate the editorial suggestions first with `python "<helper>" reconcile --dry-run --project-root "<project>" --suggestions "<scratch-json>"`, then publish with the same command without `--dry-run`. Dry-run uses the same exact-snapshot and proposal validation as reconciliation and reports User/AI counts and `valid_snapshot`; it does not acquire locks, invalidate, append logs, or publish anything. It is not approval, a prerequisite audit, or a guarantee against later concurrent changes; normal publication still audits prerequisites and revalidates. Use an external scratch location, not another canonical registry. The envelope is `{"inputs": <exact context inputs>, "processed": <all input paths>, "suggestions": [...]}`. Every suggestion needs a stable, agent-chosen `key` (reuse it on reruns), `script` (project-relative approved DOCX path), integer `start` and `end`, exact whitespace-normalized `passage`, `extracts` (list of context extract IDs; empty for full-script-only applicability), `type`, `brief`, and `notes` (editorial rationale). Allowed types: `B-roll`, `Graphic`, `Still`, `Animation`, `Screen Recording`, `Audio`, `Other`. Do not fabricate model output in Python: the helper only imports, validates, reconciles, and reports coverage. Preserve prior suggestion keys by inspecting the registry's Source Key and Proposal fields. Omitted previous suggestions become inactive rather than disappearing.
5. Open `Asset Registry.md` in the OneDrive stage directory for human review. Each compact card has a stable ID and a short literal excerpt from the original proposed brief as its descriptive title, followed by Review, Type/Origin, Source/Extracts, Passage, Asset (brief), and Why (rationale). The title is derived from the saved proposal, so human brief edits do not change its identity. Edit Review to `Pending Review`, `Keep`, or `Reject`. Edit Type, Asset, Why, Passage, and Extracts in place. Extracts accepts explicit IDs such as `EXTRACT-2, EXTRACT-5`, or `Full film only`, not JSON or inferred titles. Source is a read-only script filename label; precise paths and word ranges remain in evidence. Asset and Why are ordinary wrapping paragraphs, including multiple lines and blank lines; preserve their bold label delimiters and field order. Passage uses `> ` on every line, including blank lines. Literal backslashes, backticks, asterisks, angle brackets and hash signs in prose must be backslash-escaped; generated prose does this automatically. Empty and trailing-newline rationale values are preserved. Unsupported ambiguous syntax, unknown text, duplicated fields, deleted cards, changed IDs, and altered read-only labels fail explicitly rather than disappearing on save. There are no per-field headings, per-card machine blocks, or metadata footer. All source keys, paths, ranges, active/change flags, provenance, proposals, input evidence, history, control and migration snapshots live in `Asset Registry.json`. Do not edit that evidence or delete rejected cards. A removed source becomes inactive and must be rejected; old anchors in inactive rejected cards are not current applicability claims. To resolve changed proposals, inspect that asset's Change/Proposal in JSON (or the context command), update human fields as needed, then select Keep/Reject. Changed inputs reset review conservatively; unchanged reruns preserve decisions.
6. Run `python "<helper>" inspect --project-root "<project>"` before handoff and after human edits. This read-only JSON report validates every pending row, collects row errors, counts reviews/origins/activity, and reports exact input currency and comment import completeness. Proposed coverage is the union of active Pending Review and Keep ranges, explicitly not approved; kept coverage includes only active Keep ranges. Rejected and inactive ranges never contribute. Invalid ranges are excluded and reported as errors. Pending review and missing empty-slate confirmation appear as completion issues, not structural errors; pending review alone exits successfully with `completion_ready: false`. Genuine errors (including missing/malformed registries) exit nonzero with a summary. Inspection never approves or records anything. Only after human review resolves all Pending Review rows, run `python "<helper>" check --project-root "<project>"`. This unchanged strict, read-only completion gate prints kept advisory coverage on success. For an empty or all-rejected current slate, obtain explicit human confirmation first, then run `python "<helper>" confirm-empty --project-root "<project>" --by "<human>" --reason "<confirmed decision>"`. This records a registry-bound attestation, not automatic approval. Never call it based on an agent's own judgment. Any change to the slate, review decisions, or input evidence expires it. In a nonempty kept slate it is not needed.
7. Completion requires both canonical files, all current inputs processed, valid unique IDs/origins/types/briefs/anchors/references, no Pending Review assets, inactive assets rejected, and the empty-slate confirmation when applicable. Then use only shared `stage_completion.py record --project-root "<project>" --stage 1.4`. The shared recorder inventories and fingerprints both registry files and inputs, checks ancestors, and validates the candidate. No separate approved copy, approval-folder move, active XLSX registry, custom DONE writer, or local invalidation graph is permitted. Append normal attempt/failure/handoff/completion entries to the stage LOG using the root helper.

## Reruns and Scope

Compact cards use plain newlines, not trailing backslashes, trailing-space hard breaks, or HTML breaks. Keep card source compact: no blank line after its heading or between related metadata lines. Asset and Why values start beside their labels and may contain human-authored multiline paragraphs. Keep the blank line after the passage blockquote, and one blank line between cards and after the introduction. Fenced fields, per-field headings, embedded metadata, spaced cards, and hard-break cards are unsupported; there is no conversion or reformat command. Literal escaped backslashes in prose remain supported.

The optional JSON `migration` field is opaque historical evidence. Helpers preserve and checksum it without interpreting its contents, accessing its referenced backups, or using it for review or completion decisions. It is passive history, not executable format support.

Reconciliation preserves existing human field edits, decisions, JSON evidence and rejection history. Unchanged reruns preserve both files and their mtimes. New proposals are pending. A changed underlying proposal, comment range, input fingerprint, or applicability resets review and records the prior decision. Human edits to brief/type/notes/anchors are merged field-by-field rather than overwritten; reviewers must resolve any conflicts against Proposal. Existing AI assets omitted by the new analysis are retired and never automatically resurrected as new IDs. Comment identity is script-relative path plus Word comment ID, not its changing text. Renaming a script is a new source and retires the old asset. Removed inactive cards stay in the registry to prevent duplicate imports and retain history. Save editor changes before helper mutations; do not edit concurrently with publication. Missing, malformed, checksummed-tampered or identity/label-mismatched JSON fails rather than being regenerated. Markdown human fields are not checksummed against JSON and remain editable.

Pair publication cannot be atomic: each changed file is replaced atomically while `.assets-publication.json` blocks readers. A failed replacement rolls back already replaced files from byte-exact temporary backups. If interrupted or rollback fails, the guard and `.assets-recovery-*` files remain: stop, inspect the guard's target/previous mapping, restore both previous files (a null previous means the target did not exist), verify the restoration, then remove the guard before retrying. Never simply delete the guard and accept a potentially torn pair.

This stage plans assets only. It does not acquire media, manage later media versions, license files, assign final edit timestamps, or own downstream asset approval. Coverage is a union of kept word ranges, not a measure of production quality or a requirement to fill every frame.
